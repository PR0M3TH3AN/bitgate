# Governance lists on the wire

BitGate's allow and block lists are ordinary signed Nostr events. This page is
the format. A second implementation is held to the vectors in
[`vectors/governance-lists/`](../vectors/governance-lists/), not to BitGate's
code. The vectors are generated by `scripts/build-list-vectors.mjs`, and
`npm test` fails if they drift from it. Every case is read at the file's `now`
and, unless the case gives a root (`reader.root`, or `query.root` when
choosing), with the subject's own key as the root.

There are two families:

- **Application-wide lists:** "who is allowed or blocked in this application".
  They are signed by keys the application's root authorizes.
- **Scoped lists:** "who is allowed into, or blocked from, this one thing",
  usually a world. By default they are signed by that thing's own author, or
  by the keys the reader was given for it. There is no roster, no curator and
  no service.

Both use kind **30078** (NIP-78 application data). They are addressable and
replaceable: the newest `created_at` wins, and a tie goes to the
lexicographically smallest event id.

## Telling a list from other kind-30078 events

Kind 30078 is shared. A BitUnlock listing is `30078:<seller>:<name>`, for
example. The rules for telling them apart:

1. **Ask for exactly the list you want.** Filter relays by `kinds: [30078]`,
   `authors: [<signer>]` and `#d: [<the exact d below>]`. Never fetch "an
   author's 30078 events" and guess which are lists.
2. **The `d` grammar is the discriminator.** A governance `d` is
   `<namespace>:governance:<scope>:v<version>`, with an optional
   `:<subject coordinate>` on the end. Nothing else is read as a governance
   list.
3. **The tags must agree with the `d`.**
   - A scoped list requires exactly one `v`, one `scope` and one `subject` tag,
     each equal to its part of the `d`.
   - An application-wide list may omit `scope`. If it is present, it must equal
     the scope in the `d`, or the event is refused.
   - The `client` tag is informational and never required.

An event that matches by accident (a listing named
`x:governance:user-deny:v1`) is still not read. A scoped reader needs the
`subject`, `v` and `scope` tags to agree as well. Only a seller can collide
with their own list this way, so other kind-30078 names are not narrowed.

## Scoped lists (v1)

### Grammar

```
d          = namespace ":governance:" scope ":v1:" subject
namespace  = 1*64( %x61-7A / DIGIT / "." / "_" / "-" )  ; lowercase; first character a letter or digit
scope      = "user-allow" / "user-deny"
subject    = kind ":" pubkey ":" identifier
kind       = "0" / ( %x31-39 0*4DIGIT )                  ; decimal, no leading zero, at most 65535
pubkey     = 64( DIGIT / %x61-66 )                       ; lowercase hex
identifier = 1*( any character except U+0000-U+001F and U+007F )
             ; 1 to 512 bytes of UTF-8; colons allowed; compared exactly
```

- **Reading the subject:** the kind, a colon, 64 hex characters, a colon, and
  then **the rest is the name**. It is never split on further colons, so a
  world's `d` can contain colons, spaces and any printable text. For an NSWP
  world the subject is `37300:<64 hex>:<the world's d>`.
- There is no trimming and no Unicode normalization. The identifier must equal
  the world's own `d` byte for byte, as relays compare `d`.

### Tags

| Tag | Required | Value |
| --- | --- | --- |
| `d` | exactly one | as above |
| `v` | exactly one | `"1"` |
| `scope` | exactly one | equal to the scope in `d` |
| `subject` | exactly one | equal to the subject in `d` |
| `p` | 0 to 2,000 | one person each: `["p", <64 lowercase hex>]`. Further fields are ignored |
| `client` | optional | ignored. A reader never refuses a list for what it says or for its absence |
| anything else | — | ignored |

- **The content is empty.**
- An allow list and a block list are **two separate events** for the same
  subject, one per scope. Each replaces independently. Because a block always
  beats an invitation, publishing the block first is always safe.

### Reading one event

The checks run in this order. The first that fails refuses the whole event,
with this code:

| # | Check | Refusal |
| --- | --- | --- |
| 0 | the reader has a signature check to run | `no_verifier` |
| 1 | it is a signed event (`id`, `pubkey`, `sig` in lowercase hex; `kind` and `created_at` integers; tags arrays of strings) | `not_an_event` |
| 2 | `kind` is 30078 | `wrong_kind` |
| 3 | exactly one `d`, and it matches `namespace ":governance:" scope ":v" version ":" rest` | `bad_d` |
| 4 | the version is `1` | `unsupported_version` |
| 5 | the scope is `user-allow` or `user-deny` | `unsupported_scope` |
| 6 | the subject matches the grammar | `bad_subject` |
| 7 | exactly one `v`, `scope` and `subject` tag, each equal to `d`'s part | `tag_mismatch` |
| 8 | the event's `pubkey` is a key of the root the reader was given (by default the subject's `pubkey`; see "Who may sign") | `wrong_signer` |
| 9 | the content is empty | `content_not_empty` |
| 10 | at most 2,000 `p` tags, counting malformed ones | `too_many_entries` |
| 11 | `created_at` is at most 600 seconds (ten minutes) ahead of the reader's clock. This refusal applies to an event read on its own; when choosing among copies, such an event is dropped before choosing instead | `from_the_future` |
| 12 | the NIP-01 id and signature are valid | `bad_signature` |

Then the entries:
- each `p` tag whose value is 64 lowercase hex characters is one person;
- duplicates collapse;
- a `p` tag with any other value is skipped and counted, never read loosely as
  an npub or uppercase hex. One bad entry does not discard the owner's whole
  list.

Over 2,000 `p` tags refuses the event. A reader does not read the first 2,000.

### Who may sign

A list counts when it is signed by **the root the reader was given** for the
subject. The reader supplies the root, which is why this is a reader's rule and
not a field in the event:

- **By default** the root is the subject's own key, the key in its coordinate
  (for a world, the key that announced it). Leave the root out, and this is the
  rule.
- **A reader may be given a root instead:** one key, or a list of at most four.
  For example, a world announced by a deploy key kept in a file can name its
  owner's everyday key, so the owner can change the list from the menus while
  signed in. The NSWP kit takes the root from the world's own manifest;
  BitGate needs to know nothing about manifests.
- **A given root replaces the default; it does not add to it.** If the
  subject's own key should still count, it must be in the root.
- **Where the root comes from is the reader's decision.** It must be something
  the subject itself vouches for. Taking it from the list event would let
  anyone name themselves.
- **One list across several root keys:** each key's copy is its own
  replaceable event (Nostr replaces per author). Across all root keys, the
  newest copy is the list.

Evaluate against `scopedListAuthority(subject, root)`, using the same root the
lists were read with. Every root key may allow and block, none of them can be
blocked from their own subject, and the first is the engine's root.

### Choosing the current list

From whatever relays returned, **candidates** are the events that:
- are kind 30078;
- are signed by a root key;
- have exactly the expected `d`;
- carry a valid signature.

So an unsigned event under a root key, however new, cannot replace the list.

**A list dated in the future is not a candidate.** A candidate whose
`created_at` is more than 600 seconds after the reader's own `now` is dropped
**before choosing**; it is not refused as the newest. A fast clock therefore
cannot pin a list in place, and a malformed future-dated event cannot make the
list unreadable. Such an event stands once its time comes within ten minutes.
The reader **says it saw one**: the reference reader lists the dropped ids in
`futureDated`, and an application should show it to the owner (for example,
"a change dated in the future was ignored").

The newest remaining candidate wins (ties go to the smallest id), and then it
is read in full. If that newest candidate is refused, **the list is
unreadable**; an older copy is not used in its place, because it was
replaced.

A reader keeps three states apart and says which one it is in:

- **Empty:** a valid list that names nobody.
- **Not found:** no candidate at all, including when every copy was dropped as
  future-dated.
- **Unreadable:** the newest candidate was refused, with a reason code.

What to do with "not found" or "unreadable" is the application's call.
BitGate's recommendation for a world:
- an invitation list that is not found or unreadable lets **nobody** in but
  the owner, and says why;
- a block list that is not found means nobody is blocked;
- an unreadable block list is shown to the visitor and the owner as unreadable,
  not silently ignored.

### Evaluating

- Build **one snapshot per subject**, with the subject's owner as root:
  `createAuthorityState({ root: owner })`.
- Turn each list into a contribution (`scopedListToContribution`), and
  evaluate with the `allowlist` preset when the world is by invitation.
- **Never merge a scoped list into an application-wide snapshot,** where it
  would apply everywhere.
- **Blocked beats allowed.** A block is applied first, and an invitation never
  lifts it (`packages/core/src/evaluator.js`, steps 6 and 7).
- **The owner is the root.** The root can never be blocked, so the owner
  always gets into their own world.

### Privacy

A v1 list is public: anyone can read who is invited and who is blocked.
Applications must say so to the owner. A public block list tells the world
whom the owner blocked.

Hidden entries are not part of v1, and the empty-content rule is what keeps
them out. Hashing keys hides nothing, because pubkeys are public. Encrypting to
the owner alone hides the list from the very visitors who need to check it.
Hidden lists need a group key, and they will come as a new version, which a v1
reader refuses rather than misreads.

### For NSWP

- **Namespace:** `nswp`, in every client.
- **Writers stop at 500 entries.** Readers accept up to 2,000. A 2,000-entry
  list is about 144 KB, and many relays refuse events over 64 KB.
- **"Every world of mine"** for a block is not a scoped list. It is the
  existing application-wide `nswp:governance:user-deny:v1`, signed by the
  owner and read with `decodeContribution`, with the owner as root.
- **An allow list with no `p` tags** means nobody but the owner, and must not
  read as "no allow list".
- **Whether a world is by invitation at all** is the world's manifest's word,
  not the presence of an allow list. Nothing in the list says it.

### Reference reader

`@bitgate/nostr` exports:
- `decodeScopedList(event, { verify, root?, now? })` and
  `resolveScopedList(events, { namespace, scope, subject, verify, root?, now? })`.
  The second returns `futureDated` with every result;
- `encodeScopedList({ namespace, scope, subject, entries })`;
- `scopedListAuthority(subject, root?)` and `scopedListToContribution(list)`,
  plus the grammar helpers.

`root` is one 64-hex key or a list of one to four, and defaults to the
subject's own key. `now` is unix seconds and defaults
to the system clock; the vectors give it explicitly, so every reader is tested
at the same moment.

`verify` is required; pass `verifyEvent` from `@bitgate/verify` or your own
NIP-01 check. There is no unverified mode. Anything but `true` counts as a
failed check, including a promise.

## Curation sets (kind 30004, NSWP-08 lists)

BitPortal and the NSWP kit already keep their lists of worlds as NIP-51
curation sets: a host's allow list under `d = "bitportal"`, a curator's
starter set, and any list a visitor follows. BitGate reads them **as they
are**, exactly as NSWP-08 (`protocol/08-lists.md` in the NSWP repository)
defines them. A curator never publishes the same worlds again in a second
format.

**Structure** (`parseCurationSet`) follows NSWP's own reader issue for issue,
and is held to NSWP's vectors, copied unchanged and pinned by hash in
[`vectors/nswp/`](../vectors/nswp/):

- kind 30004, with a `d`; title and description come from the first `title`
  and `description` tags;
- entries are the `a` tags of the form `<digits>:<64 lowercase hex>:<non-empty
  name>` whose kind, read as a number, is 37300 (a world). Each is written
  back as `37300:…`. Anything else on the list is passed over without
  complaint;
- each entry counts once, in the curator's order;
- ceilings: 200 entries (`too_many_worlds` warning, the rest not read), title
  200 and description 1,000 characters (cut, with a `value_too_long` warning),
  and `d` at most 128 characters (a `value_too_long` error). "Characters" are
  JavaScript string lengths, as NSWP measures them;
- no title means the title is the `d`. A list with no worlds is still a list.

**For governance** (`readCurationSet`), a signature check is required; a list
is its curator's word and nobody else's. Refusals: `no_verifier`, `invalid`
(with NSWP's error codes, including `not_signed`) and `bad_signature`.

**The current copy** (`resolveCurationSet({ coordinate, now })`, or
`{ pubkey, d, now }`) is chosen exactly as NSWP-08 chooses it (NSWP's
`resolveList`):

- The list's coordinate `30004:<pubkey>:<d>` fixes the key.
- Candidates are kind-30004 events signed by that key, with **exactly one**
  `d` tag equal to the list's, and a valid signature. Each id counts once.
- **A copy dated more than 600 seconds after the reader's `now` is left out
  before choosing**, and named in `futureDated`, so a copy signed with a fast
  clock cannot stand over every honest newer one. Exactly 600 seconds ahead
  is still chosen.
- The newest of the rest wins; a tie goes to the smallest id.
- If the newest can't be read, there is no list, and an older copy never
  stands in for it.
- With no candidate the result is `not_found`. A client that already holds a
  copy keeps it, as NSWP-08 says.

This is held to NSWP's own `choosing` vectors in `vectors/nswp/lists.json`.

**As an allowlist:** `curationSetToContribution(list)` gives an
`address-allow` contribution, or `address-deny` if asked, with the curator as
actor. It counts only where the curator holds the capability. The root does,
so a host's list becomes what may be shown under the `allowlist` preset; a
block still beats it. The vectors are in
`vectors/governance-lists/curation-sets.json`, generated by
`scripts/build-curation-set-vectors.mjs`.

## Application-wide lists

```
d = namespace ":governance:" scope ":v1"      ; namespace has no ":"
```

| Scope | Entries |
| --- | --- |
| `user-allow`, `user-deny`, `trust-seed` | `["p", <64 lowercase hex>]` |
| `event-allow`, `event-deny` | `["e", <64 lowercase hex>]` |
| `address-allow`, `address-deny` | `["a", "<kind>:<64 lowercase hex>:<d>"]` |

- **Who counts:** any signer may publish a list. It counts only if the signer
  holds the matching `contribute-<scope>` capability under the application's
  root, resolved when lists are combined (`packages/core/src/adminState.js`).
- **Who holds `contribute-*-allow`:** only `super_admin`, unless the root's
  role document grants it with a `cap` tag. A `curator` can block but not allow
  by default.
- **Changes in this version:**
  - a `scope` tag that disagrees with the `d` refuses the event; it used to
    override it;
  - entries are read only in lowercase hex. An npub or uppercase hex in an
    event is skipped; those forms are for input typed by a person, not for the
    wire;
  - `event-allow` and `address-allow` are new. An event or address passes an
    allowlist on its own entry or on its author's.
- **No entry cap for application-wide lists,** unlike scoped lists. Refusing a
  long moderator block list would unblock everyone on it. A cap here needs its
  own decision.

## Named lists

One curator keeps several lists: who may sell, who may be paid a share, which
listings are blocked. An application-wide list is one replaceable event per
signer, namespace and scope, so each named list has a namespace of its own.
This section is the vocabulary. Readers in other projects are held to
`vectors/governance-lists/named-lists.json` (generated by
`scripts/build-named-list-vectors.mjs`). The reference is `namedLists.js` in
`@bitgate/nostr`.

| Name | `d` | An entry means |
| --- | --- | --- |
| `sellers` | `bitunlock.sellers:governance:user-allow:v1` | this key may sell |
| `payees` | `bitunlock.payees:governance:user-allow:v1` | this key may be paid a share of a sale |
| `listings-allowed` | `bitunlock.listings:governance:address-allow:v1` | this listing is on the curated list (read only while listings are curated) |
| `listings-blocked` | `bitunlock.listings:governance:address-deny:v1` | this listing may not be sold |
| `people-blocked` | `bitunlock.people:governance:user-deny:v1` | this person may neither sell nor be paid |

Entries are `p` tags (people) or `a` tags (listings), in the
application-wide format above, with two rules shared with BitUnlock so that the
two always agree:

- **A person is 64 lowercase hex characters,** as BitUnlock stores keys.
- **A listing is its coordinate and nothing else:** never an event id, so a
  block survives the seller republishing the listing as a new event. The
  coordinate follows BitUnlock's one rule (`src/protocol/product-coordinate.ts`;
  the kit's `cleanListing` is the same):

  ```
  ^30078:[0-9a-f]{64}:[^:\r\n][^\r\n]{0,255}$
  ```

  The name is 1 to 256 characters (JavaScript string length) on one line, and
  does not start with a colon. Spaces, and colons after the first character,
  are allowed. Names are compared exactly, with no trimming
  (`parseListingCoordinate`, `LISTING_COORDINATE`).
- **An entry that doesn't fit is skipped and counted** (`skipped`). The rest of
  the list stands.

**Which lists each decision reads.** Every answer is the **transaction**
dimension:

| Decision | Lists | A key or listing not on an allow list |
| --- | --- | --- |
| `may-sell` | `sellers`, `people-blocked` | denied |
| `may-be-paid` | `payees`, `people-blocked` | denied |
| `may-sell-listing` | `listings-blocked`, `people-blocked` (through the listing's seller) | allowed unless blocked |
| `may-sell-listing-curated` | `listings-allowed`, `listings-blocked`, `people-blocked` | denied (see below) |

- **Blocked beats allowed** in every decision.
- **The root is never gated.**
- **Payable is not the same as able to sell:** a key on `payees` alone may be
  paid but not sell.
- **`may-sell-listing-curated` is the owner's word to switch on.** BitUnlock
  has no counterpart today: any listing from an allowed seller may be sold.
  Comparing it in shadow is fine, but enforcing it is stricter than today and
  would stop existing listings. Switching it on is decided by the owner at the
  time, not by any session.

**Who counts.** The root's role document (`<deployment>:governance:roles:v1`,
signed by the root) names each curator with the role `list-curator`. That role
holds `contribute-user-allow`, `contribute-user-deny`,
`contribute-address-allow` and `contribute-address-deny`, and nothing else
(`NAMED_LIST_ROLES`). Anyone can publish a list under these names; only a
curator's or the root's counts. Every list is read with a signature check, and
a copy that fails it is dropped.

**Choosing the current copy** (`resolveNamedLists`):
- Each named list is a replaceable event per signer and `d`, so relays can
  return several copies.
- **Signatures are checked before choosing.** A copy tampered with after
  signing keeps the genuine id and can claim a later `created_at`. A reader
  that picked the newest copy first and checked it afterwards would let that
  forgery push the genuine list out.
- Only copies that pass are candidates. The newest per signer and `d` is the
  list (ties go to the smallest id), and a replaced copy no longer counts.
- The vectors hold both rules: a tampered, newer `payees` copy, and a
  replaced `sellers` copy.

**Worlds are not here.** A host's list of worlds and a curator's starter set
are NSWP-08 curation sets, read as they are (above).

**The names are given.** The four namespaces and the `list-curator` role were
given by the fleet's orchestrator on 2026-11-21 (NSWP `docs/fleet.md`, "Names
given"). Change one only after asking there.

## Checking signatures on the headless path

Every reader that decides something takes a `verify` function and refuses to
run without one: `decodeScopedList`, `resolveScopedList`, `readCurationSet`,
`resolveCurationSet` and `readNamedList`, and, for the application-wide
formats, `readLabelContributions` (NIP-32), `readContributionLists` (kind
30078) and `resolveVerifiedRoster` (kind-30000 role sets). Each of the last
three throws a `TypeError` without a verifier, and reports how many events it
dropped (`dropped.unverified`). Only signed copies are candidates for
replacement, so no unsigned event can replace a list.

`verify` is a NIP-01 check that returns `true`: `verifyEvent` from
`@bitgate/verify`, or the one an application already ships. Anything else
counts as a failed check, including a promise. The standalone `bitgate.js`
carries no crypto, so it takes the application's own check.

The structure-only codecs (`decodeLabels`, `labelsToContributions`,
`decodeContribution`, `resolveAuthorityRoster`, `parseCurationSet`) are
unchanged, for callers that verify upstream, as the runtime does.
